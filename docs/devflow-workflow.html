Luồng làm việc devflow

Ai làm gì từ lúc nhận việc tới lúc phát hành, và mỗi bước bị chặn bởi cổng nào: chọn cỡ S / M / L, worktree riêng, gate, verifier độc lập, verify-app, hook, và (ở chế độ GitHub) PR + CI. Nội dung khớp với plugin devflow 0.11, docs/AGENT_WORKFLOW.md và skill dev-loop.

Tổng quan

Một task = một nhánh = một worktree = một lần đưa vào nhánh tích hợp. Mặc định chạy local (gate local thay CI); đặt "mode": "github" thì cùng gate đó chạy thêm trong CI của pull request.

Local   feat/… fix/…  ──land (gate + fast-forward)──►  dev  ──promote (ff + tag vX.Y.Z)──►  main
                                                        └──────── push sao lưu ────────────────┘

GitHub  feat/… fix/… claude/…  ──npm run pr──►  pull request  ──CI: cùng gate + review──►  merge trên GitHub
                                (gate local, push nhánh, mở PR)                                   └── npm run release → tag vX.Y.Z

Người viết ≠ người kiểm

Verifier chạy ở context mới, so diff với plan đã duyệt. Agent không tự chấm bài của mình.

Luật máy kiểm được thì giao cho máy

Rule, lint, test, hook. CLAUDE.md giữ ngắn (~50 dòng); quy trình nằm trong skill, chỉ nạp khi dùng.

Độ nặng theo cỡ task

S không plan, M plan ngắn, L đi OpenSpec. Gate và land giữ nguyên ở mọi cỡ.

Chứng minh trên app thật

Gate xanh chưa đủ: skill verify-app của dự án chạy app và trả bằng chứng theo từng tính năng.

Sơ đồ workflow

Màu theo vai trò: xanh tím là người dùng, xanh ngọc là agent, vàng đất là máy (gate, hook, script). Hình thoi là điểm quyết định. Bảng "Chi tiết từng bước" bên dưới đi sâu vào từng pha.

Cỡ S / M / L

dev-loop chọn cỡ trước tiên. Cỡ lớn thêm plan và spec; gate và land giữ nguyên.

Phân loại: OpenSpec hay làm thẳng

Agent đi theo cây này ở bước 0.5 của dev-loop và nói kết quả cùng lý do trong một dòng.

Không dùng OpenSpec (S / M)

  • fix đưa hành vi về đúng như đã định, ≤ ~3 file, không đổi schema
  • Chỉnh UI nhỏ, refactor không đổi hành vi
  • test, docs, chore, style, nâng version thư viện
  • Thêm một field hiển thị hoặc một bộ lọc đơn giản

Với OpenSpec (L)

Propose luôn chạy trong worktree (không tạo openspec/changes/ ở checkout dev). Sau khi duyệt, /opsx:apply bắt buộc chạy trong subagent context sạch; archive sau khi land bằng npm run archive.

Ai làm gì theo thời gian

Bốn đường đi theo thời gian: hot-fix trên dev, rồi task cỡ S, M, L. Mũi tên nét liền là yêu cầu / lệnh, nét đứt là kết quả trả về. Ở chế độ GitHub, "land" đọc là "npm run pr + người merge trên GitHub, CI chạy cùng gate".

Cách viết mô tả, thay đổi, lập kế hoạch

Bốn nguyên tắc chống các lỗi hay gặp khi LLM viết code, cộng ba mẫu dùng lại: yêu cầu, plan, báo cáo. Nguyên tắc nằm trong mục "Cách viết thay đổi" của CLAUDE.md và được verifier kiểm.

1Nghĩ trước khi code

Nêu giả định. Yêu cầu có nhiều cách hiểu thì liệt kê và hỏi, không tự chọn âm thầm. Có cách đơn giản hơn thì nói.

2Ít code nhất đủ giải quyết

Không tính năng ngoài yêu cầu, không abstraction cho code dùng một lần, không cấu hình hay xử lý lỗi thừa.

3Chỉ sửa chỗ cần sửa

Mỗi dòng đổi truy được về yêu cầu. Thấy code chết không liên quan thì báo, không xoá; không tiện tay đổi format.

4Làm theo mục tiêu kiểm chứng được

Tiêu chí kèm cách chứng minh, plan dạng bước → kiểm bằng gì, test viết trước, bằng chứng thật trong báo cáo.

Mô tả yêu cầu

Viết lại thành acceptance criteria. Thiếu thông tin thì hỏi lại, không đoán.

Khi <điều kiện / thao tác>
thì <kết quả quan sát được>.
Chứng minh bằng: <test | lệnh | verify-app>

Phạm vi: <module · màn hình · vai trò>
Dữ liệu cũ: <có / không đụng>
Giả định: <...>

Bảng ví dụ (đổi quy tắc nghiệp vụ, bug logic)

Bắt buộc khi đổi quy tắc nghiệp vụ hoặc sửa bug logic. Gồm ca thường, ca biên và ca không được phép. Agent được nháp nhưng không tự bịa kết quả mong đợi.

| # | Dữ liệu có sẵn | Thao tác | Kết quả mong đợi | Nguồn |
| 1 | <trước> | <thao tác> | <kết quả> | người dùng |
| 2 | <...>   | <...>      | <...>     | chưa xác nhận |

Dòng chưa xác nhận là lỗ hổng; dòng chạm tiền hoặc dữ liệu quan trọng phải được xác nhận trước khi code.

Lập kế hoạch

Trong plan mode (chỉ đọc), lặp với người dùng tới khi ổn. Chỉ trả lời mục áp dụng cho task. Cỡ S chỉ cần một dòng.

0. Giả định (nhiều cách hiểu → hỏi)
1. Bước → kiểm bằng gì (file sẽ sửa)
2. Ranh giới: type / interface mới, ai sở hữu
3. Schema / dữ liệu cũ (dry-run, idempotent)
4. Transaction / đồng thời
5. Ma trận test: tiêu chí → tầng → tên test
6. Rollback nếu release lỗi
7. Chế độ land: auto-land | manual (+ lý do)

Ma trận test (người dùng quyết)

Mỗi tiêu chí hoặc dòng ví dụ ánh xạ tới một tầng test; người dùng giữ, cắt hoặc bỏ. Bỏ thì ghi rõ trong plan và báo cáo. Mặc định fix: test tái hiện ở đúng tầng lỗi, viết trước, phải đỏ trước khi sửa.

  • Quy tắc tính toán, điều kiện hợp lệ → unit
  • Transaction, constraint, query → integration (DB thật)
  • Luồng nhiều màn hình, phân quyền UI → E2E
  • Tính năng chạy thật → verify-app

Commit và nhánh

1 task = 1 nhánh = 1 lần land. Commit nhỏ theo từng bước của plan, nhánh > ~400 dòng (không tính test / generated) thì tách.

nhánh:  feat|fix|chore/<scope>-<mô-tả>
commit: feat(<scope>): <mô tả ngắn>
        <body: quyết định còn giá trị, root cause>

# Conventional Commits; commitlint chặn sai dạng.
# Scope = tên module / package.

Ranh giới của agent

Agent không bao giờ

  • Tự merge PR, hoặc tự promote / release khi chưa được yêu cầu riêng
  • Chạm dữ liệu production (data-tool, SQL tay) mà chưa có người duyệt
  • Xoá, skip hoặc disable test, bớt assertion để cho xanh
  • "Fix" bằng try/catch nuốt lỗi
  • Force-push, push tay lên nhánh bảo vệ, dời / merge / reset --hard nhánh tích hợp (hook chặn)
  • Sửa tay version trong versionFiles
  • Commit secret, tự bịa kết quả mong đợi trong bảng ví dụ
  • Tiện tay refactor ngoài yêu cầu

Agent tự làm

Analyze, code, test, check, verify-app, verifier, self-review, ship, báo cáo, đề xuất bài học. Chế độ GitHub: mở PR khi gate xanh và verifier PASS, sửa CI đỏ. auto-land khi plan đã duyệt chọn và đủ điều kiện.

Agent hỏi / dừng

Yêu cầu mơ hồ, vùng xám giữa các cỡ, schema / phân quyền / API do reviewer đề nghị, circuit breaker (sửa 2 lần vẫn đỏ, task phình, review quá 3 vòng). Vùng buộc manual trong CLAUDE.md luôn chờ người bảo land.

Queue và chạy song song

.claude/task-queue.md (ở main checkout, gitignore, mọi worktree dùng chung một bản) trả lời ba câu: còn việc gì, việc nào làm được ngay, việc nào đang kẹt. Phần dưới là cấu trúc minh hoạ, không phải dữ liệu thật.

Một dòng cho một outcome

Task lớn trỏ tới OpenSpec change; chi tiết nằm ở openspec/changes/<change>/tasks.md, không sao chép vào queue.

Ready = hết blocker

Thứ tự trong Ready là ưu tiên do người sắp. Agent chỉ chọn task đầu tiên thật sự ready. Blocker lộ ra giữa chừng thì dừng và báo, không tự đảo thứ tự.

Claim bằng nhánh + worktree

queue start --branch đánh dấu In progress và tạo worktree; claim trùng bị từ chối. Mỗi task một session + một nhánh + một worktree, không để hai agent sửa cùng một module.

Park, không bỏ quên

queue block T-XXX --reason kèm /devflow:handoff khi phải chờ; queue unblock khi hết chờ. Done giữ ~7 ngày rồi prune; lịch sử lâu dài nằm trong git log.

Giữa các session

Ghi chú ngắn (≤ 30 dòng) trên nhánh để session sau hoặc agent khác tiếp tục ngay, không phải đọc lại codebase.

Lưu: /devflow:handoff

Chạy khi dừng giữa chừng: hết phiên, chờ người dùng, context sắp đầy. Commit lên nhánh (cloud: push) vì file chưa push sẽ mất khi session bị thu hồi.

Đọc: tự động khi mở session

  • Hook SessionStart in ghi chú của nhánh hiện tại và tóm tắt queue
  • /devflow:handoff resume: đối chiếu với git log và lệnh test; lệch thì tin code

Vị trí và dọn dẹp

  • OpenSpec: openspec/changes/<name>/handoff.md; task nhỏ: .claude/handoff/<nhánh>.md
  • Trước khi land / mở PR: chuyển quyết định vào commit hoặc mô tả PR, xoá ghi chú và file plan

Dọn worktree kẹt

Luôn thử luồng chuẩn trước: land → untask. Chỉ dùng worktrees:clean khi untask hoặc ExitWorktree không gỡ được (còn thư mục sau Permission denied, No-op vì worktree từ session cũ, thư mục Git không còn biết). Chạy ở đâu cũng được, script tự về main checkout.

LệnhTác dụng
npm run worktrees:cleanChỉ liệt kê, đánh dấu an toàn hay rủi ro. Không đổi gì
… -- --yesXoá mục an toàn: nhánh đã vào nhánh tích hợp và cây sạch, thư mục mồ côi, đăng ký worktree đã stale; xoá luôn nhánh đã vào
… -- --yes <tên>Chỉ xử lý mục có tên nhánh / thư mục đó
… -- --yes --forceMất việc chưa commit Xoá cả mục rủi ro (còn thay đổi hoặc nhánh chưa vào)

Script gỡ junction / symlink (node_modules, .husky/_) trước khi xoá nên không xoá nhầm sang main checkout. Đừng đứng terminal / IDE bên trong thư mục đang xoá (Windows khoá thư mục).

Thiết lập để các cổng có hiệu lực

Hook chỉ hoạt động trong repo có .devflow.json; cài plugin không đổi hành vi ở dự án khác.

  1. Chạy /devflow:init một lần trong dự án (thêm --github cho chế độ PR + CI). Có bản mới của plugin thì chạy lại để cập nhật scripts/devflow/.
  2. Điền section devflow trong CLAUDE.md: lệnh build / test, vùng buộc manual, luật cần phán đoán.
  3. Khai báo vùng gate trong .devflow.json (areas: eslint, commands, format) và bật "stopGate": true.
  4. Dự án có app chạy được: /devflow:verify-setup để tạo .claude/skills/verify-app/.
  5. Chế độ GitHub: thêm bước cài đặt vào devflow-gate.yml, đặt check "devflow gate" thành required, chọn kiểu merge.

Trang này đi cùng plugin devflow. Chi tiết từng skill nằm trong plugins/devflow/skills/, mẫu cấu hình trong plugins/devflow/kit/templates/.
